# 회고: Gemini 실검증 + 공개 전환 (2026-08-06)

*이 문서는 운영 문서가 아니라 회고 기록입니다. 다른 문서처럼
`docs/index.md`에 걸리거나 영/한 쌍으로 관리되지 않고, 이 하루 동안의
작업을 나중에 되짚어보기 위한 개인 기록입니다.*

## 무엇을 했나

하루 동안 세 갈래 작업이 이어졌다. 순서대로:

1. **Gemini CLI 실검증** — Phase 5부터 v0.2.0 릴리스까지, Gemini 관련
   테스트는 전부 가짜 mock 셸스크립트로만 돌렸었다. 실제 `gemini`
   바이너리(v0.54.0, 미인증 상태)를 처음으로 직접 실행하고, 번들된 JS
   소스코드까지 읽어서 진짜 동작을 추적했다.
2. **저장소 공개 전환** — 테스터에게 테스트를 요청했는데 저장소가
   비공개라 접근이 막혀있던 걸 뒤늦게 발견, 점검 후 Public으로 전환.
3. **전체 재검토** — 위 두 작업의 diff를 신선한 시각(서브에이전트)으로
   다시 리뷰했고, 실제로 재현되는 회귀 버그를 하나 더 찾아 고쳤다.

## 잘한 것

- **"진짜로 실행해서 확인한다"는 원칙이 실제로 버그를 잡았다.**
  `docs/research-gemini-cli.md`는 Gemini의 공식 문서만 보고 작성된
  추정이었는데, 실제 CLI를 돌려보니 두 가지가 문서와 달랐다:
  - 에러 JSON이 stdout이 아니라 **stderr**로 나간다 (성공 시에만
    stdout). 소스코드에서 `coreEvents.emitFeedback("error", ...)` →
    `writeToStderr`까지 직접 추적해서 확인했다.
  - 인증 실패의 `error.type`이 문서가 암시하던 `"AuthError"`가 아니라
    그냥 `"Error"`였다.
  둘 다 리뷰나 문서만으로는 절대 못 잡았을 종류의 버그다. mock으로
  아무리 테스트를 촘촘히 짜도, mock 자체가 틀린 가정 위에 있으면
  의미가 없다는 걸 다시 확인한 케이스.
- **공개 전환 전에 실제로 점검을 했다.** "그냥 스위치만 누르면 되는
  일"처럼 보이지만, `git log --all -p`로 112개 커밋 전체를 시크릿
  패턴으로 훑고, 오래된 "비공개 저장소" 전제 문구들을 찾아 고치고,
  Windows 인스톨러를 CI 원본 아티팩트와 byte-for-byte 대조까지 하고
  나서 전환했다. 되돌리기 까다로운 작업이라 사용자 확인도 먼저 받았다.
- **재검토 요청에 실제로 새 버그가 나왔다.** `auth method`라는 정규식을
  추가한 게, 정상적인 성공 응답에도 걸려서 오분류를 일으키는 회귀였다.
  직접 재현 스크립트로 확인하고 나서야 진짜라는 걸 확신했고("에이전트가
  그렇다니까 그런가보다"가 아니라), 고친 뒤에도 다시 재현 스크립트로
  확인했다. 이 패턴(발견 → 직접 재현 → 수정 → 재현으로 재확인)이 이
  프로젝트 전체에서 반복되는 작업 방식이고, 오늘도 정확히 그렇게
  진행됐다.

## 아쉬웠던 것 / 배운 것

- **"검증된 수정"도 회귀를 만들 수 있다.** 첫 Gemini 수정
  (stdout/stderr 분리, 에러 패턴 확장)은 실제 CLI로 검증까지 마치고
  커밋했는데, 정작 그 수정 자체가 부작용(정상 응답 오분류)을 낳았다.
  "실제로 재현해서 고쳤다"는 게 "이 변경이 다른 경로에 영향을 안
  준다"는 걸 보장하진 않는다는 걸 다시 배웠다. `classify_handoff()`의
  두 번째 검사 루프(구조화된 에러가 없을 때 raw 텍스트 전체를 훑는
  fallback)가 있다는 걸 처음 패치할 때 충분히 고려하지 못했다 — 새
  정규식을 추가할 때마다 "이 패턴이 정상적인 답변 텍스트에도 우연히
  걸릴 수 있는가"를 매번 따로 체크해야 한다는 게 이번에 명확해졌다.
- **재검토를 "같은 사람"이 아니라 "새로운 시각"으로 했다.** 이번엔
  서브에이전트에게 사전 맥락 없이 diff만 주고 리뷰를 시켰는데, 정작 내가
  직접 짠 코드의 허점을 내가 스스로 다시 봤으면 놓쳤을 가능성이 높다
  (같은 맹점으로 다시 봤을 것이므로). "전체 재검토" 요청이 들어왔을 때
  스스로 다시 훑기보다 독립된 시각을 붙이는 게 더 효과적이었다.
- **문서 정합성은 한 번에 다 안 잡힌다.** 공개 전환 문구 수정을 1차로
  했을 때 README/release-process만 고치고, `docs/cli-reference.md`와
  `handoff_bridge.py`의 주석에 남아있던 "비공개라서" 근거는 놓쳤다 —
  재검토 단계에서야 잡혔다. "private" 텍스트를 grep으로 훑을 때
  범위를 처음부터 넓게 잡았어야 했는데, 처음엔 사용자에게 직접
  보여지는 문서(README)만 우선순위로 봤다.
- **`docs/security-model.md`의 DEC-24 근거는 아직 미해결로 남겨뒀다.**
  "실사용자는 운영자뿐"이라는 전제가 테스터가 생기며 약해졌는데, 이건
  결정을 뒤집을지 말지 사용자가 판단할 문제라 손대지 않았다. 앞으로
  테스터가 늘거나 실제 배포 규모가 커지면 다시 짚어야 할 항목.

## 다음에 비슷한 상황이면

- 새 정규식/패턴을 에러 분류기에 추가할 때는, "이게 정상 케이스의 raw
  텍스트에도 우연히 매치될 수 있는가"를 추가하는 시점에 바로
  점검한다 — 나중에 재검토에서 잡히길 기다리지 않는다.

  코드 주석 + 모든 docs로 넓게 잡는다.
- "재검토해줘" 같은 요청이 오면, 직접 다시 훑기보다 사전 맥락 없는
  새 에이전트에게 diff만 주고 검토시키는 쪽이 더 잘 걸러진다는 걸
  다시 확인했다 — 계속 이 패턴을 쓴다.
